# 审阅批注模式

## 1. 目的与模式

批注模式把合并过程中的模型判断显式交还给人复核。它不改变“模板控制格式、子文档控制技术事实”的权威顺序，也不能用批注为无依据的技术改写开脱。

合并计划登记 `review_comments.mode`：

- `review`：保留并新增真实 Word 批注；用户要求审阅稿或本次存在需人工裁定的模型判断时使用；
- `auto`：仅当触发项存在时生成批注，否则交付无批注稿；默认采用；
- `clean`：不新增批注，并在用户明确要求最终清稿时移除已有审阅批注；不得由“最终文件”一词自行推断为 `clean`。

若某项判断可能改变技术事实、承诺、指标或关系，保持原文并暂停该项变动，集中询问；继续不受影响的合并。低风险结构与表达建议可按合并契约生成带批注的审阅稿。

## 2. 必须批注的触发项

在 `review` 或被触发的 `auto` 模式中，下列事项必须进入批注清单：

1. **结构补齐**：源稿缺少分项标题，模型依据其他权威位置补出标题、编号或层级；
2. **结构拆分/合并**：把同一源段中的标题与正文拆开，或把多个源段合为一个新结构，且读者需要知道原稿结构发生了变化；
3. **衔接补写**：正文中加入原稿没有的承上启下句、解释句或逻辑关系；
4. **综合编写**：总体目标、总体技术方案、摘要或综合验证等文字不是任一源稿的逐字内容，而是依据多稿综合形成；
5. **位置调整**：源稿内容从其原章节移到模板中的另一语义角色，例如把某研究分项的局部“总体技术方案”移入该分项的“关键技术解决途径”；
6. **待裁定事项**：存在两种均合理的标题、层级、位置、术语或关系表达，当前采用其中一种但不影响继续生成；
7. **资料例外**：缺失参考文献条目、无法闭合的原稿引文或其他经用户授权原样保留的不规范项。

纯格式规范化、按模板机械重编号、完全一致重复的授权删除、确定字段的无歧义回填以及图片等比例缩放通常不加批注；这些操作仍进入内部审计记录。若其中存在解释空间，则按上述类别批注。

## 3. 批注类别与写法

批注使用固定前缀，便于筛选：

- `[结构补齐]`
- `[结构调整]`
- `[衔接补写]`
- `[综合编写]`
- `[位置调整]`
- `[待裁定]`
- `[资料例外]`

正文保持正式文本，不能插入“AI生成”“待确认”等内联标记。每条批注用简洁的三段式信息：

```text
[类别] 处理：本稿做了什么。
依据：来自哪个模板要求、子文档或用户指令。
请确认：需要人工决定或复核什么；若无须操作则写“请确认此处理是否保留”。
```

不得使用“可能有问题”之类无定位、无依据的泛化提示。批注不评价作者，也不替作者作最终技术裁定。

## 4. 锚定与去重

- 批注锚定到实际受影响的标题、衔接句、综合段首或迁移后分项标题；不统一堆到章节末尾。
- 一项连续处理只加一条批注，覆盖其最小充分范围；同一理由影响多个离散位置时分别锚定。
- 锚点文字在最终文档中必须唯一；不唯一时使用完整容器路径、段落 ID 或书签定位，不能让工具随意命中第一处。
- 结构补齐标题与位置调整发生在同一段时，可以合并为一条批注，但必须同时说明两项处理。
- 保留源稿已有批注并使用不冲突的新 ID；如需区分，新增批注作者统一为“合稿助手”。

## 5. 批注清单

在写入 DOCX 前生成 `review_comments_manifest.json`：

```json
{
  "mode": "review",
  "author": "合稿助手",
  "comments": [
    {
      "id": "decision-001",
      "category": "位置调整",
      "anchor_contains": "最终文档中的唯一锚点",
      "source": ["子文档B.docx/原章节"],
      "operation": "移入模板的目标章节",
      "reason": "模板章节职责及用户指令",
      "needs_human_decision": true,
      "comment_text": "[位置调整] 处理：……\n依据：……\n请确认：……"
    }
  ]
}
```

所有模型新增文字和有解释空间的位置调整，必须能够在清单或明确的“不需批注”审计项中找到。清单只作为内部 QA 依据，不另行交付，除非用户要求。v3 将清单放入 review_comments，并在 decisions 中登记未决项；交付级别与是否清除批注分别控制。

## 6. 写入与结构验收

使用 `documents` Skill 的 `tasks/comments_manage.md` 与 `ooxml/comments.md` 写入真实 Word 批注；优先运行本 Skill 的 `scripts/apply_review_comments.py INPUT.docx review_comments_manifest.json OUTPUT.docx`，由它先验证锚点唯一性，再写入符合 Documents comments 规范的原生批注，并保持 `w:pPr` 位于段落首位。重复标题可增加 `anchor_block_id` 指向最终主文档中的真实段落；正文其他 part 的特殊批注锚点交专项适配器处理。不得用脚注、括号文字、隐藏文字或高亮模拟批注。

写入后：

1. 运行 `documents/scripts/comments_extract.py`，逐条核对作者、正文和锚定片段；
2. 运行本 Skill 的 `scripts/audit_review_comments.py OUTPUT.docx --manifest review_comments_manifest.json`；
3. 确认 `comments.xml`、关系和内容类型存在；每个批注 ID 恰有开始、结束、引用和批注正文；
4. 确认清单中的每个必需锚点恰好命中并有正确类别，所有带 `w:pPr` 的批注段落仍以 `w:pPr` 为第一个子元素；
5. 重新渲染正文，确认加入批注锚点没有造成文字、分页或对象漂移。批注气泡不一定出现在 headless 渲染中，因此视觉检查不能代替结构检查。

`clean` 模式只能在用户明确要求后使用 `comments_strip.py`；移除后还要复核正文没有随锚点一起丢失。
